# Протокол обхода репозитория

## Назначение

Этот документ устанавливает обязательный порядок анализа объектов конфигурации 1С:ЗУП в репозитории XML-выгрузки. Его цель — исключить выводы, не подтверждённые структурой репозитория, XML-описаниями или BSL-кодом.

Протокол применяется совместно с `AI_RULES.md`, `PERPLEXITY_USAGE.md` и `METADATA_MAP.md`. При противоречии приоритет имеют правила из `AI_RULES.md` и фактические файлы репозитория.

## Обязательная подготовка

Перед началом анализа задачи необходимо:

1. Прочитать `AI_RULES.md`.
2. Прочитать `PERPLEXITY_USAGE.md`.
3. Прочитать `METADATA_MAP.md`.
4. Прочитать этот документ.
5. Определить режим работы: `ANALYZE`, `DESIGN` или `IMPLEMENT`.
6. Зафиксировать целевой объект, предполагаемые связанные объекты и границы задачи.

Если целевой объект не определён или существует несколько одноимённых/похожих вариантов, сначала выполнить поиск и не начинать реализацию до идентификации точного объекта.

## Источники подтверждения

| Что требуется установить | Допустимый источник |
|---|---|
| Существование объекта и его тип | `Configuration.xml`, XML конкретного объекта |
| Реквизиты, табличные части, формы, команды, макеты, роли, состав объекта | XML конкретного объекта и XML вложенных объектов |
| Наличие файла или каталога | Фактическое дерево репозитория |
| Алгоритм, обработчик, экспортная процедура/функция, клиент-серверный вызов | Найденный `.bsl` |
| Фактический результат в рабочей базе, права пользователя, данные и производительность | Тестовая база или отдельно предоставленные результаты теста |

Название элемента не доказывает его существование, назначение или алгоритм.

## Алгоритм обхода объекта

Каждый объект рассматривается как пара:

- XML-описание: `ИмяОбъекта.xml`
- Одноимённый каталог: `ИмяОбъекта/`

Выполняйте шаги в указанной последовательности.

### 1. Найти объект в конфигурации

1. Найти объект в `Configuration.xml`.
2. Определить тип метаданных и путь XML-описания.
3. Открыть XML конкретного объекта.
4. Выписать подтверждённые вложенные элементы: реквизиты, табличные части, формы, команды, макеты, роли и другие дочерние объекты.

### 2. Проверить каталог объекта

1. Проверить наличие одноимённого каталога объекта.
2. Рекурсивно просмотреть его фактическое дерево.
3. Отдельно проверить `ext/`, если он существует.
4. Найти все файлы `.bsl`, `.xml` и `.mxl` в каталоге объекта и вложенных каталогах.
5. Сопоставить найденные файлы с составом, подтверждённым XML.

### 3. Проверить формы

Для каждой формы, подтверждённой XML объекта, обязательно:

1. Открыть XML-описание формы.
2. Проверить каталог формы: `ИмяОбъекта/forms/ИмяФормы/`.
3. Проверить каталог модуля формы: `ИмяОбъекта/forms/ИмяФормы/ext/`.
4. Рекурсивно проверить дочерние каталоги формы.
5. Найти все `.bsl`, `.xml` и `.mxl`, включая файлы во вложенных `ext/`.
6. Сопоставить элементы формы, команды и обработчики с XML и BSL.

Если XML формы найден, отсутствие одноимённого каталога формы или `ext/` нужно зафиксировать как проверенный результат, а не как предположение.

### 4. Проверить подтверждённые вложенные объекты

Если XML объекта подтверждает команды, макеты или другие дочерние элементы, проверить их XML и одноимённые каталоги. Рекурсивно искать `.bsl` во всех релевантных каталогах `ext/`.

### 5. Сформировать manifest

Перед выводами подготовить manifest:

| Категория | Что фиксировать |
|---|---|
| XML | Конфигурация, объект, формы, команды, макеты и другие использованные XML |
| Каталоги | Каталог объекта, `ext/`, `forms/`, каталоги форм, дочерние каталоги |
| BSL | Все найденные и просмотренные `.bsl`, назначение, релевантные процедуры/функции |
| MXL | Найденные и релевантные макеты `.mxl` |
| Ограничения | Недоступные, непроверенные или отсутствующие ожидаемые пути |

## Правило «код не найден»

Фраза «BSL-код не найден в репозитории» допустима только после выполнения полного обхода, следующего из XML и фактического дерева. В ответе необходимо явно перечислить:

1. Проверенные XML-файлы.
2. Проверенные каталоги объекта.
3. Проверенные формы и их каталоги.
4. Проверенные `ext/` и вложенные `ext/`.
5. Все найденные `.bsl`.
6. Ожидаемые, но отсутствующие пути.
7. Пути, которые не удалось проверить, и причину ограничения.

Нельзя делать этот вывод только потому, что BSL не виден рядом с XML-файлом или в каталоге верхнего уровня.

## Режимы работы

### ANALYZE

Используется для поиска объекта, карты структуры и существующей логики. Не создавать и не предлагать изменения как готовую реализацию, пока не определено точное место доработки.

### DESIGN

Используется, когда задача понятна, но данных XML/BSL недостаточно для безопасной реализации. Предлагать только минимальный проект, явно помечать непроверенные места и перечислять проверки в тестовой базе.

### IMPLEMENT

Используется только после подтверждения целевого объекта, точки входа, модулей и затрагиваемых элементов. Вносить минимальные точечные изменения. Для нового или исправленного BSL применять `bsl-code-style`.

## Безопасные границы реализации

- Не придумывать реквизиты, команды, формы, общие модули, подписки на события, параметры сеанса или серверные вызовы.
- Не переписывать неподтверждённые участки модуля целиком.
- Не выполнять автоматическое проведение, удаление, массовое изменение данных или регламентно значимые действия без явного требования задачи и подтверждения механизмом репозитория.
- Для новой точки входа указать источник вызова: команда формы, кнопка, обработчик события, экспортная процедура или иной подтверждённый механизм.
- Разделять клиентский, серверный и серверный без контекста код в соответствии с подтверждённой архитектурой вызовов.

## Статусы доказательств

Используйте один из статусов для важных утверждений:

- `ПОДТВЕРЖДЕНО XML` — структура найдена в XML.
- `ПОДТВЕРЖДЕНО BSL` — логика найдена в BSL.
- `ПОДТВЕРЖДЕНО ДЕРЕВОМ` — файл или каталог найден в репозитории.
- `НЕ ПОДТВЕРЖДЕНО` — данных для вывода нет.
- `ПРЕДЛОЖЕНИЕ ПРОЕКТА` — безопасный вариант реализации, не являющийся фактом о конфигурации.
- `ТРЕБУЕТ ПРОВЕРКИ В БАЗЕ` — факт нельзя установить по XML/BSL; нужна тестовая база.

## Итоговая проверка перед ответом

Перед завершением ответа проверить:

- Целевой объект идентифицирован.
- Просмотрены необходимые XML и каталоги.
- Для релевантных форм проверены XML, каталоги форм и вложенные `ext/`.
- Все использованные BSL перечислены.
- Факты отделены от предложений проекта.
- Неподтверждённые места и риски перечислены.
- Подготовлен план тестирования в копии базы.
