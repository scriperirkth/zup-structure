# Протокол обхода репозитория

## Назначение

Документ устанавливает порядок анализа объектов конфигурации 1С:ЗУП в XML-выгрузке, чтобы выводы опирались на структуру репозитория, XML-описания и BSL-код.

Приоритет: явный запрос пользователя, затем `AI_RULES.md`, затем этот документ. Пути, статусы и формулировка «не найдено» определены в `AI_RULES.md` (разделы 2, 6, 7).

## Подготовка

1. Прочитать `AI_RULES.md`.
2. Прочитать `PERPLEXITY_USAGE.md` и `METADATA_MAP.md`, если нужны шаблоны запросов и карта каталогов.
3. Определить режим: `ANALYZE`, `DESIGN` или `IMPLEMENT` (или режимы, заданные запросом пользователя).
4. Зафиксировать целевой объект, связанные объекты и границы задачи.

Если целевой объект не определён или есть несколько похожих вариантов, сначала выполнить поиск и идентифицировать точный объект.

## Источники подтверждения

| Что требуется установить | Допустимый источник |
|---|---|
| Существование объекта и его тип | `Configuration.xml`, XML конкретного объекта |
| Реквизиты, табличные части, формы, команды, макеты | XML объекта и XML вложенных объектов |
| Наличие файла или каталога | Фактическое дерево репозитория |
| Алгоритм, обработчик, экспортная процедура, клиент-серверный вызов | Прочитанный `.bsl` |
| Результат в рабочей базе, права, данные, производительность | Тестовая база или предоставленные результаты теста |

Название элемента не доказывает его существование, назначение или алгоритм.

## Алгоритм обхода объекта

Объект представлен парой: XML-описание `<Папка>/<Имя>.xml` и одноимённый каталог `<Папка>/<Имя>/`. Регистр имён каталогов важен: `Ext`, `Forms`, `Templates`.

### 1. Найти объект

1. Найти объект в `Configuration.xml` и определить тип.
2. Открыть `<Папка>/<Имя>.xml`.
3. Выписать подтверждённые вложенные элементы: реквизиты, табличные части, формы, команды, макеты.

### 2. Проверить каталог объекта

1. Листингом проверить `<Папка>/<Имя>/`.
2. Просмотреть `Ext/` и найти `.bsl`, `.xml`, `.mxl`.
3. Сопоставить найденные файлы с составом, подтверждённым XML.

### 3. Проверить формы

Для каждой формы, подтверждённой XML объекта:

1. Открыть `<Папка>/<Имя>/Forms/<Форма>.xml`.
2. Листингом проверить `<Папка>/<Имя>/Forms/<Форма>/Ext/` (там `Form.xml` и каталог `Form/`).
3. Листингом проверить каталог `Form/` и найти модуль формы.
4. Сопоставить элементы формы, команды и обработчики с XML и BSL.

Отсутствие ожидаемого каталога фиксировать как проверенный результат, а не как предположение.

### 4. Проверить вложенные объекты

Если XML подтверждает команды, макеты или другие дочерние элементы, проверить их XML и каталоги (`Templates/` и др.).

### 5. Список использованных файлов

По умолчанию достаточно краткого списка: путь и результат проверки. Развёрнутый manifest (XML, каталоги, BSL, MXL, ограничения) составлять по запросу пользователя или при выводе «код не найден».

## Правило «код не найден»

Вывод «BSL-код не найден в просмотренном» допустим после листинга `Ext/` объекта и каталогов форм, подтверждённых XML. В ответе перечислить:

1. Проверенные XML.
2. Проверенные каталоги (`Ext/`, `Forms/<Форма>/Ext/`, `Forms/<Форма>/Ext/Form/`).
3. Найденные `.bsl`.
4. Ожидаемые, но отсутствующие пути.
5. Пути, которые не удалось проверить, и причину.

Нельзя делать этот вывод только потому, что BSL не виден рядом с XML-файлом объекта. Вывод об отсутствии кода в рабочей базе по репозиторию делать нельзя.

## Режимы работы

### ANALYZE

Поиск объекта, карта структуры и существующая логика. Готовую реализацию не выдавать, пока не определено место доработки.

### DESIGN

Задача понятна, но данных XML/BSL недостаточно для безопасной реализации. Предлагать минимальный проект, помечать непроверенное и перечислять проверки в тестовой базе.

### IMPLEMENT

Точечная реализация. По умолчанию — после подтверждения целевого объекта, точки входа и затрагиваемых элементов. Если запрос пользователя прямо требует код при неполном подтверждении, выдавать код с явными допущениями: непроверенные части получают статус `ПРЕДЛОЖЕНИЕ ПРОЕКТА` или `ТРЕБУЕТ ПРОВЕРКИ В БАЗЕ`. Для BSL применять `bsl-code-style`.

## Безопасные границы реализации

- Не придумывать реквизиты, команды, формы, общие модули, подписки на события, параметры сеанса или серверные вызовы.
- Не переписывать неподтверждённые участки модуля целиком.
- Не добавлять проведение, удаление, массовое изменение данных или регламентно значимые действия без явного требования задачи.
- Для новой точки входа указать источник вызова: команда формы, кнопка, обработчик события, экспортная процедура или иной подтверждённый механизм.
- Разделять клиентский, серверный и серверный без контекста код в соответствии с подтверждённой архитектурой вызовов.

## Статусы доказательств

Набор статусов определён в `AI_RULES.md`, раздел 6.

## Итоговая проверка перед ответом

- Целевой объект идентифицирован.
- Просмотрены необходимые XML и каталоги.
- Для релевантных форм проверены XML, каталоги форм и модули.
- Использованные BSL перечислены.
- Факты отделены от предложений проекта.
- Неподтверждённые места и риски перечислены.
- Подготовлен план тестирования в копии базы.
